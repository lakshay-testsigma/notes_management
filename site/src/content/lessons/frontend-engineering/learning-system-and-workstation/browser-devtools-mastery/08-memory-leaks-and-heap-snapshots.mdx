Your single-page app gets slower each hour a user keeps it open. That is the usual symptom of a memory leak: a bug that makes the page use more and more memory over time. The Task Manager shows that memory grows. It cannot show which object holds it. The Memory panel can.

The garbage collector frees an object only when no path of references leads to it from a GC root, such as `window`. A DOM node is detached when you remove it from the DOM tree but JavaScript still references it. Detached nodes are a common cause of leaks. Predict the result of this code from the Chrome docs.

<PredictReveal

  reasoning="#leaf keeps a reference to its parent, so a path still runs from window through leafRef and #leaf up to #tree. The whole subtree is detached, but reachable."

After the first two cuts, #tree still hangs from Window through leafRef. Only the third cut leaves both DOM nodes with no path, so the collector can free them. In a heap snapshot, the Retainers section lists exactly these paths: the objects that point to the object you select.

<Depth level="internals">

A heap snapshot records every object in the JavaScript heap at one moment. Shallow size is the memory an object holds itself. Retained size is the memory you free when you delete the object and everything that only it keeps reachable. A detached tree often has a small shallow size and a large retained size. Distance is the length of the shortest path to a root.

</Depth>

<Depth level="production">

To confirm a leak, take a snapshot, do an action and reverse it, such as open and close a dialog, then take a second snapshot. The Comparison view shows the objects that were not freed. The filter "Objects retained by detached nodes" finds them fast. The Allocation timeline shows when new memory appears. Objects you used in the Console can also stay alive, and the filter "Objects retained by the DevTools console" shows them.

</Depth>
