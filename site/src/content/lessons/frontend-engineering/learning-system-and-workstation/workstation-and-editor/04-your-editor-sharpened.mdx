You clone a team's frontend repository, open it, and your editor indents with tabs while every merged change uses two spaces. You reformat one file by accident and the diff turns into a mess. The team already fixed this, and the answer is sitting in the repo.

VS Code keeps every **setting** — a named option such as format-on-save — in a **scope**, the place that holds it. **User settings** live in a `settings.json` on your machine and apply to every project you open. **Workspace settings** live in a `.vscode/settings.json` inside one repository, apply only to that project, and travel with it through version control.

Read the map from the top. The same change can land in one of two scopes, and only the workspace one reaches the team.

**Note.** VS Code allows settings that name an executable, such as `git.path` or `terminal.external.*`, only in the user scope. A committed workspace could otherwise point your editor at a command it should not run.

<Depth level="internals">
When two scopes set the same option, VS Code resolves them in a fixed order: `default`, then `user`, then `remote`, then `workspace`, then `workspace folder`, then a language-specific setting, then an organisation `policy`. A scope further right wins, so the most specific and most shared rule always beats a general personal one.
</Depth>
