Fluency needs the model under `add`, `commit` and `push`. A commit stores a snapshot, the author, a message and pointers to its parent commits. A branch is a 41-byte file that holds the checksum of one commit, so it is cheap. `HEAD` points to the branch you are on, and each new commit moves that branch forward.

Say `main` and `feature` both grew from commit C2. A merge takes the two tips and their common ancestor, does a three-way merge, and records a new merge commit with two parents. A rebase replays each commit of your branch on top of the other branch, as a new commit.

In the lab, run merge, then rebase, from one fork.

<Experience id="git-graph-lab" />

The merge kept C3 and added C5. The rebase replaced C3 with a copy, C3', so history became a straight line. Merge keeps the true record; rebase rewrites it into a clean line. Pro Git's rule: "Do not rebase commits that exist outside your repository and that people may have based work on." Teammates who hold the old commits get duplicates. So rebase local work before you push, and merge what is shared.

A merge conflict happens when both branches change the same part of a file. Git stops and marks it with `<<<<<<<`, `=======` and `>>>>>>>`. Edit the file, run `git add`, then `git commit`.

Before a pull request, tidy your branch. `git commit --amend` replaces the last commit. `git rebase -i` lists recent commits, oldest first, as a script to edit. Both make new commits, so rewrite only commits you have not pushed.

```bash
git commit --amend --no-edit   # add a forgotten staged file to the last commit
git rebase -i HEAD~3           # edit the last three commits (HEAD~3 = three commits back)
```

```text
pick   f7f3f6d Add cart total       # keep as it is
squash 310154e Show total in header # join with the line above, merge both messages
fixup  a5f4a0d Fix typo             # join, drop this message
reword 9b29157 Add tax line         # keep the change, edit the message
# move a line to reorder; delete a line to drop that commit
```

<Depth level="internals">

When the other branch is directly ahead, `git merge` makes no new commit. It only moves your branch label forward: a fast-forward. A rebase works in steps. Git finds the common ancestor and takes the diff of each commit on your branch. It resets your branch to the target and applies each saved diff in turn. Then `git merge` on the target fast-forwards it.

</Depth>

<Depth level="production">

Teams disagree about history. One side keeps it as a record of what happened; the other tidies it into a clear story. Pro Git advises the middle way: rebase local work before you push, and never rebase what you pushed. If a teammate rebased shared commits anyway, `git pull --rebase` can help. It works only when the rewritten commits are nearly identical to the old ones.

A squashed branch reads as one clear change, but the reviewer loses your small steps. If a rebase goes wrong, `git rebase --abort` returns you to the start; after it ends, `git reflog` finds the old tip. Practice: make three commits, squash them with `git rebase -i HEAD~3`, and check `git log --oneline`. The `gh` CLI, lazygit and GitLens are tool options for this work.

</Depth>
