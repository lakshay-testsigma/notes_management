A terminal is the window where you type. The shell is the program inside it that reads and runs commands. Bash and zsh are shells; iTerm2, Warp and Ghostty are terminals; Oh My Zsh and Starship style the prompt.

You want each 404 path in `access.log`, with a count. One line does it: `cat access.log | grep 404 | sort | uniq -c | sort -rn`. A pipeline is a chain of commands joined by `|`: Bash connects the output of each command to the input of the next.

Redirection sends a stream to a file. Standard output (stdout) carries results; standard error (stderr) carries errors. `ls > dirlist 2>&1` sends both to `dirlist`. Text pipelines cost precision: `grep 404` also matches a size of 404 bytes.

An environment variable is a `name=value` pair that each command inherits. PATH lists the directories where Bash searches for commands; a miss fails with status 127.

{/* <!-- concept: shell-startup-files-and-aliases --> */}

An `export` typed at the prompt lasts only for that shell. Each new shell first runs its startup files: an interactive shell reads `~/.bashrc`, and a login shell reads `~/.bash_profile`. So put a permanent fix there:

```bash
# ~/.bashrc: interactive shells. Login shells read /etc/profile, then the first of
# ~/.bash_profile, ~/.bash_login, ~/.profile.
echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.bashrc
echo "alias gs='git status'" >> ~/.bashrc
source ~/.bashrc   # load it into the open shell now
```

An alias replaces the first word of a command with longer text, so `gs` runs `git status`. Aliases save typing, but scripts ignore them. zsh has its own startup files.

The shell also creates your SSH key pair for Git hosting. The private key stays on your machine; you paste the public `.pub` text into your Git host's settings. Full steps: the vault note `ssh-keys-for-git-workstation-and-editor`.

```bash
ls ~/.ssh                # check for an existing key pair first
ssh-keygen -o            # create one; enter a passphrase when asked
ls ~/.ssh/*.pub          # the new public key; its name depends on the key type
cat ~/.ssh/<name>.pub    # copy this text to your Git host
```

<Depth level="internals">

Bash runs each command of a multi-command pipeline in its own subshell, a separate process. The exit status of a pipeline is the status of its last command, so `false | sort` succeeds. With `set -o pipefail`, the pipeline returns the status of the rightmost command that failed. Order matters: `ls 2>&1 > dirlist` sends only stdout to the file. Bash remembers where it found each command in a hash table and searches PATH again only when the name is not in that table.

A login shell does not read `~/.bashrc` by itself. So `~/.bash_profile` usually contains `if [ -f ~/.bashrc ]; then . ~/.bashrc; fi`. The `.` command, also called `source`, runs a file in the current shell, so its exports stay. An alias cannot take arguments; use a shell function when you need them.

</Depth>

<Depth level="production">

After you install a tool, run `type <name>` to see which file Bash will run. An empty entry in PATH, such as a trailing colon, means the current directory. **Interpretation.** Remove such an entry: with it, a file in any folder you `cd` into can run as a command.

SSH or HTTPS: HTTPS needs no key; a credential helper such as macOS Keychain stores your login. Many hosts now want a personal access token, not your password. Over SSH, all traffic is encrypted and authenticated by your key, but SSH has no anonymous access. With a passphrase, the `-o` option stores the private key in a format that resists brute-force cracking, and `ssh-agent` saves you from typing the passphrase each time. This is Pro Git (2014) advice; check your host's current key advice. Keep the private file out of repositories and shared drives.

Practice: add the alias above, open a new terminal, and run `gs`. Then run `bash -c gs`. It fails: a non-interactive shell does not read `~/.bashrc` and does not expand aliases.

</Depth>
