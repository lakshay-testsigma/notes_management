Private practice has one weak point: nobody checks it. To build in public means you share your work while you learn: code in public repositories, short posts about what you learned, and contributions to other projects.

The GitHub Open Source Guide gives the benefit. All open source work is public, so you get free examples that show what you can do. MDN's interview advice agrees: create a portfolio, build real projects, and contribute to open source. MDN also says to write about a useful answer, because writing makes the concept clear to you and brings feedback. The roadmap gives the same advice for blogging.

A pull request is a proposed change to a repository that maintainers review before they merge it. Trace the path from the guide below. Watch where a small fix and a bigger change split.

<Diagram id="first-contribution-path" />

The README explains the project, and the CONTRIBUTING file explains how to help. The issue tracker shows the current work. A typo fix can go straight to a pull request. A bigger change starts with a comment or an issue.

{/* <!-- concept: reproducible-bug-report --> */}

An issue can also report a bug. The guide asks you to give context: say what you were trying to do and how to reproduce the error.

<Depth level="internals" title="Write a bug report with steps to reproduce">

The guide contrasts two reports. "X doesn't happen when I do Y" helps. "X is broken! Please fix it." does not. **Interpretation.** A good report is a minimal reproduction: the fewest steps that still show the bug.

1. Write what you tried to do.
2. List the steps that make the error happen.
3. Say what you expected and what you saw.

The benefit: a maintainer sees the bug at once and does not guess. The trade-off is your time, because you must remove steps until only the cause is left. The failure mode is the vague "it doesn't work" issue. The maintainer must ask questions first, and the issue can wait or close.

Practice: a form does not submit, and you write "Login is broken." Rewrite it. Check: your report names the page, the steps (open login, type an email, click Submit), the expected result, and the actual result.

</Depth>

The main failure is to skip that discussion. The guide compares it to a stranger who joins a party and talks about llamas while the group discusses goldfish. People may then not hear your idea. The trade-off is time and public feedback. Start small: fix a broken link in documentation you use.
