A page loads 30 files over a phone network that loses some packets. The HTTP messages stay the same in every version. The version decides how much one lost packet costs.

Head-of-line blocking means a stuck first item holds up every item behind it. HTTP/1.1 sends one request at a time per connection, so browsers open several TCP connections. HTTP/2 adds multiplexing: it splits messages into binary frames on many streams inside one TCP connection. But TCP delivers bytes only in order and cannot see the streams. One lost packet stalls all of them. HTTP/3 runs over QUIC, a transport on UDP. Each request gets its own QUIC stream, and a loss delays only that stream. QUIC names each connection with a connection ID, not IP addresses. So a download continues when a phone moves from Wi-Fi to mobile data. HTTP/2 ties its connection to IP addresses and cannot do this (MDN WebTransport API, "Better network transitions").

In the lab, pick a version and step through one lost packet. Predict which responses stall, then check your prediction.

<Experience id="http-versions-lab" />

The benefit is real on lossy networks, but HTTP/3 has costs. Firewalls that block UDP force a fallback to HTTP/2 over TCP, which also loses this migration. 0-RTT early data lets a returning client send a request in its first flight, but an attacker can replay it. HTTP/1.1 workarounds, such as domain sharding across extra hostnames, now hurt: they split the one shared connection.

<Depth level="internals">

A client picks HTTP/2 or HTTP/3 with ALPN, a TLS extension that lists protocol names such as `h2` and `h3`. A server can advertise HTTP/3 with the `Alt-Svc` header. Header compression matters because every request repeats the same headers and cookies. HTTP/2 compresses them with HPACK, which assumes in-order data. HTTP/3 uses QPACK instead: table updates travel on separate unidirectional streams. RFC 9114 itself defines no priority signal (Appendix A.2.1). Priorities come from a separate extension, the `Priority` request header. A QUIC client address can change during a connection (RFC 9114, Section 10.10).

</Depth>

<Depth level="production">

Sprites, many images packed into one file, were another HTTP/1 trick. On HTTP/2, bundling 1000 tiny files into one still has a trade-off. Fewer requests cost less overhead. But one changed byte forces a fetch of the whole bundle, while separate files cache one by one (High Performance Browser Networking, "Minimize Concatenation and Image Spriting").

Node's undici offers both `http/1.1` and `h2` in its ALPN list by default, with `http/1.1` first, and the server picks one (`lib/core/connect.js:76,98 @ 011d947`). The option `allowH2: false` limits the client to HTTP/1.1 (`lib/dispatcher/client.js:231 @ 011d947`). Its HTTP/2 stream cap is the smaller of 100 and the server limit. A silent stream gets a PING; without an answer, undici drops the session and moves requests to a new connection (`lib/dispatcher/client-h2.js:521-540 @ 011d947`).

</Depth>
