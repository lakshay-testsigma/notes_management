On café Wi-Fi, anyone on the network can read and change plain HTTP. TLS (Transport Layer Security) gives three promises: the server is authenticated, the data is hidden, and any change is detected. HTTPS is HTTP sent inside TLS.

A key share is half of a key exchange. Both sides combine shares to derive the same secret without ever sending it. A certificate alone can be copied, so CertificateVerify proves possession of the private key. The chain links the server's certificate to an authority the browser already trusts. A certificate authority (CA) issues certificates. Let’s Encrypt is a CA that issues them free and automatically with the ACME protocol. The video replays this order slowly.

<Video id="tls13-handshake" />

Compared with older TLS, 1.3 needs one round trip and encrypts everything after ServerHello. Every full handshake gives forward secrecy: a stolen key later cannot decrypt recorded traffic. Resumption with only a pre-shared key (PSK) does not (RFC 9846, Sections 1.3 and 2.2).

<Depth level="internals">

Resumption uses a ticket from an earlier connection as a pre-shared key and skips the certificate messages. The client may then send 0-RTT early data. That data has no forward secrecy and can be replayed, so a server accepts one 0-RTT handshake at most once per instance, and clients send only replay-safe requests (RFC 9846, Sections 2.3 and 8). TLS does not hide message length.

</Depth>

<Depth level="production">

HTTPS needs more than the handshake. The `Strict-Transport-Security` header tells the browser to use only HTTPS for the host, and an HTTPS page must not load scripts over plain HTTP (mixed content). Certificate Transparency logs record issued certificates; the server delivers the log's signed timestamp in the certificate, a TLS extension or OCSP stapling.

</Depth>
