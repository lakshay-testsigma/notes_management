On café Wi-Fi, anyone on the network can read and change plain HTTP. TLS (Transport Layer Security) gives three promises: the server is authenticated, the data is hidden, and any change is detected. HTTPS is HTTP sent inside TLS.

A key share is half of a key exchange. Both sides combine shares to derive the same secret without ever sending it. A certificate alone can be copied, so CertificateVerify proves possession of the private key. The chain links the server's certificate to an authority the browser already trusts. A certificate authority (CA) issues certificates. Let’s Encrypt is a CA that issues them free and automatically with the ACME protocol. The video replays this order slowly.

<Video id="tls13-handshake" />

Compared with older TLS, 1.3 needs one round trip and encrypts everything after ServerHello. Every full handshake gives forward secrecy: a stolen key later cannot decrypt recorded traffic. Resumption with only a pre-shared key (PSK) does not (RFC 9846, Sections 1.3 and 2.2). Resumption uses a ticket from an earlier connection and skips the certificate messages. An attacker can replay its 0-RTT early data, so clients send only replay-safe requests (RFC 9846, Sections 2.3 and 8). TLS also does not hide message length.

<Depth level="production" title="HSTS and mixed content">

A shop redirects `http://` to `https://` with a 301. The first plain-HTTP request still travels open, so an attacker on café Wi-Fi can catch it before the redirect. The `Strict-Transport-Security` header (HSTS) closes this gap: after one HTTPS visit, the browser uses only HTTPS for the host. `max-age` sets how many seconds the rule lasts. `includeSubDomains` extends it to every subdomain. `preload` asks browsers to ship the rule before the first visit. Failure mode: lock-in. A long `max-age` or a preload entry keeps forcing HTTPS, so a subdomain without a valid certificate stops working. An HTTPS page that loads files over plain HTTP has mixed content. The browser upgrades images, audio and video to HTTPS, and it blocks scripts, stylesheets, iframes and `fetch` requests (MDN HTTP docs).

</Depth>

<Depth level="production" title="Certificate transparency">

A CA can issue a certificate for your domain by mistake or after an attack. With no public record, nobody would see it. Certificate Transparency (CT) puts every issued certificate in public, append-only logs, so domain owners can watch the logs and detect a mis-issued certificate. A log returns a signed certificate timestamp (SCT) as proof of submission. The server delivers the SCT in the certificate, in a TLS extension or by OCSP stapling. Failure mode: CT does not stop a bad certificate. It only makes it visible, so you gain nothing when nobody watches the logs (MDN HTTP docs).

</Depth>
