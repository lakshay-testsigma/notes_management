Your frontend calls `fetch("/api/cart")`. The browser turns that call into a request message, and the server answers with a response message. A message is the unit that HTTP sends: a start line, header fields, an empty line and an optional body.

Read the diagram from top to bottom. Compare the two start lines: they are the only parts that differ.

<Diagram id="http-message-anatomy" />

The request start line holds a method, a target and the version. A method is the verb: `GET` reads, `POST` submits, `PUT` replaces, `DELETE` removes. The response start line holds a status code, a three-digit result. Its first digit gives the class: 2xx success, 3xx redirect, 4xx client error, 5xx server error. Headers are name-value fields about the message. The client sends `Accept: application/json`, and the server names its choice in `Content-Type`. This exchange is content negotiation.

A method is idempotent when two identical requests have the same effect as one. `GET`, `PUT` and `DELETE` are idempotent, and `POST` is not. So a client can resend a `PUT` after a broken connection, but a resent `POST` can create a second order. Correct methods give you this safety, which a "send everything as `POST`" API loses. Keep-alive lets HTTP/1.1 reuse one TCP connection for the next request and skip a new handshake.

**Note.** An API that returns `200` with an error in the body looks like a success to every tool that reads only the status code. Send the real code.

<Depth level="internals" title="Redirect, login, range and limit headers">

A redirect response puts the new URL in `Location`. With 307 and 308, the client keeps the method and the body. With 301 and 302, a `GET` stays a `GET`, but other methods may change to `GET`. With 303, the next request is always a `GET`, and the body is lost. A 401 response carries `WWW-Authenticate: Basic realm="shop"`, and the client answers with `Authorization: <type> <credentials>`. 401 means missing or invalid credentials, so a new attempt can work. 403 means valid credentials without enough rights, so the browser does not offer a new attempt. A server that sends `Accept-Ranges: bytes` accepts `Range: bytes=0-1023` and answers `206 Partial Content`. A range past the end gets `416`, and a server without range support sends the full file with `200`. `429 Too Many Requests` means too many requests in a time window, and `Retry-After: 3600` asks the client to wait 3600 seconds.

</Depth>

<Depth level="production">

Use 308 when an API endpoint moves for good: a 301 can turn a client's `POST` into a `GET`. Use 303 after a form `POST`, so a reload shows the result page and does not submit the form again. Test new redirect rules for loops, where A sends to B and B sends back to A: the browser stops with an error. Basic authentication only base64-encodes the password and does not encrypt it, so use it only over HTTPS. Bearer is a different scheme, for OAuth 2.0 tokens. Range requests let a video player seek or a download resume after a broken connection, without a new download of the whole file. Send `If-Range` with the ETag: a changed file then comes back whole, not as new bytes glued to old ones. On a 429, wait the `Retry-After` time; an instant retry keeps the client over the limit. Node's undici client uses one request at a time per connection by default (`lib/dispatcher/client.js:93-98 @ 011d947`).

</Depth>
