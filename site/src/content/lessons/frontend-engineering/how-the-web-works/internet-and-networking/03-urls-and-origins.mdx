Your app on `https://shop.example.com` calls an API on `https://shop.example.com:8443`, and the browser blocks the response. The cause is in the URL itself.

The browser runs every URL string through one parser, defined in the WHATWG URL Standard. The parser gives a **URL record**: named parts such as scheme, host, port, path, query and fragment. Special schemes have a default port, such as 443 for `https` and 80 for `http`. Each part has its own **percent-encoding** set, the rule that writes an unsafe byte as `%` plus two hex digits. So a space is `%20` in a path, but a form body writes it as `+`. So build URLs with the `URL` and `URLSearchParams` APIs: they apply the right set to each part.

The **origin** is the tuple of scheme, host and port. Change one of them and you have a new origin, so port 8443 above is a different origin. The browser lets a page read responses only from its own origin, unless the server allows more. That keeps one tab from reading your bank's data.

A **site** is wider: the scheme plus the **registrable domain**, which is the public suffix plus one label. So `shop.example.com` and `blog.example.com` are one site. SameSite cookie rules compare sites; the cookie `Domain` attribute is what lets subdomains share a cookie (page 10). But the public suffix list differs between browsers, so the standard says to prefer the origin for security decisions.

<Depth level="internals">

Parse with `new URL(input, base)`: it throws a TypeError when parsing fails. `URL.canParse()` returns a boolean, and `URL.parse()` returns null instead of throwing. The standard leaves the origin of a `file:` URL to the browser and says to use a new opaque origin when in doubt.
