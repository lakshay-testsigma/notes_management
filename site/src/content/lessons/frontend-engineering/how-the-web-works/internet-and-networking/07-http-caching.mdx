Without a cache, every visit downloads your large `app.js` again. A cache stores a response and reuses it for a later request with the same key, which is the method plus the URL. A private cache (the browser) serves one user; a shared cache (a proxy or CDN) serves many.

The server sets the rules with `Cache-Control`. A stored response is fresh while its age is less than its lifetime, for example `max-age=60`. A fresh response needs no network trip. A stale response needs validation: the browser sends `If-None-Match` with the stored `ETag` (a version tag of the response). An unchanged response gets `304 Not Modified` with headers only: no body, but still a round trip.

In the lab, change `max-age`, `no-cache` and the clock. Predict a hit, a revalidation or an origin trip before each step.

<Experience id="http-cache-lab" />

`no-cache` does not mean "do not store". It means "validate before every reuse", and `no-store` forbids storing. `Vary: Accept-Encoding` makes the cache keep one copy per value of that request header.

Hashed files such as `app.3f9a1c.js` get a long `max-age`, and the HTML gets `no-cache`. A new build changes the hash, so the HTML points to a new URL that no cache holds. This cache busting beats a short `max-age` everywhere: users get new code at once and still skip repeat downloads.

**Note.** A long `max-age` on an unhashed file is the classic failure: users keep old code until it expires, because a fresh copy never asks the origin.

<Depth level="internals">

A cache takes the lifetime from the first match: `s-maxage` (shared caches only), then `max-age`, then `Expires` minus `Date`. With none, it may guess about 10% of the time since `Last-Modified` (RFC 9111, Section 4.2). The undici client gives `immutable` a one-year lifetime only when none of these set one, and its code cites RFC 8246 (`lib/handler/cache-handler.js:1120 @ 011d947`).

</Depth>

<Depth level="production">

A shared cache must skip `private` responses and requests with `Authorization`, unless `public` or `s-maxage` allows them. `Set-Cookie` does not stop caching, so mark per-user responses `private`. `must-revalidate` makes a cache return an error, normally 504, instead of a stale copy (RFC 9111, Sections 3, 5.2.2.2, 7). Two directives allow stale copies on purpose. `stale-while-revalidate` lets a cache serve a stale response at once and revalidate it in the background. `stale-if-error` lets a cache serve a stale response when the origin answers 500, 502, 503 or 504; browsers ignore it on requests.

</Depth>
