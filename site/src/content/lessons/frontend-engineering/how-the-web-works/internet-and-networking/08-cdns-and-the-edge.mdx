Your users are in Tokyo, São Paulo and Berlin, and your origin server is in one region. A CDN (content delivery network) puts shared caches near those users. Each CDN data center is a PoP (point of presence). The browser connects to a nearby PoP, so a cached file travels a short distance and the origin gets far fewer requests.

Follow the request from left to right. Watch where the hit path stops and what the dashed purge arrow touches.

<Diagram id="cdn-request-path" />

The PoP first builds a cache key. By default it is the full URL (scheme, host, path and query) plus a few headers, such as `Origin`. On a hit, the PoP answers at once. On a miss, it asks the origin and stores the response as `Cache-Control` allows. `s-maxage` sets a lifetime for shared caches only.

A purge removes stored copies before their lifetime ends. Cloudflare can purge by URL, cache tag, hostname, prefix or everything. A purge never reaches browser caches, so hashed file names still matter.

<Depth level="internals" title="Tiered caching">

With Cloudflare Tiered Cache, PoPs form two tiers. A lower-tier PoP that misses asks an upper-tier data center first, and only the upper tier contacts the origin. Many PoPs can then share one origin fetch, so the origin gets even fewer requests.

</Depth>

**Note.** A cache key with too many parts, such as every query parameter or a cookie, splits one file into many entries. The hit rate then drops, and the origin takes the load again.

Some CDNs also run your code at the PoP (Cloudflare Workers) or resize images there (Cloudflare Images). This moves work away from the origin, but you then test and debug a second runtime.
